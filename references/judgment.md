# 判断边界

验收项只有通过和未通过。建议、背景和其他题目不进入分母，也不写成失败。审查进度用 `not_started`、`in_progress`、`blocked`、`completed` 另记。

| 实际情况 | 处理 |
|---|---|
| 必要核查做完，证据支持全部适用条件 | 该项通过 |
| 核查确认违反必要义务 | 未通过，引用原文和缺陷证据 |
| 当前材料就是全部资料，找过等效证据后仍无法证明明确要求的证据 | 未通过。写证据不足，不要推断从未执行或造假 |
| Agent 还没查完，或缺少审查环境 | 继续做，或标受阻。不记成乙方失败 |
| 标准冲突、适用条件或关键甲方事实没解决 | 受阻，写出待裁决的具体问题 |
| 候选对现有证据作了合理说明，仍无法确定某个子结论 | 按原文和实际论证判断。可以通过，同时继续核其他必需主题 |
| 评分器因基础设施、无法解析或规则歧义给出 unknown | 保留原始输出，追查原因和影响。不直接改成候选失败 |
| 合法替代被误拒、关键错误被漏放，或官方禁止的核心判定方式仍在 | 按对应的构建验收条款判未通过 |

通过需要至少一条来自交付、原题或本次执行的证据。依据原文只能证明义务是什么。`static`、`historical`、`measured` 分别对应静态核验、复核后复用的历史记录、本次实测。报告沿用这三种说法。

历史结果可以复用，但要重新核对身份、哈希、版本、适用对象和执行范围。复用不能写成新实验。

官方要求真人双审、独立审核或具名 QC 时，核查交付里有没有真实记录。甲方 Agent 不代签，也不用自己的技术检查代替这些乙方义务。

同一义务在不同轮次或不同题目上是不同实例。完全重复的出处在报告里展示一次完整判断，其余位置跳转过去。总体通过率按唯一实例计算；文件和章节按自己关联到的实例统计，不把文件通过率再平均。

零个适用项时，报告写“无适用项”，不显示 100% 通过。任一必需项未通过，总体就是未通过。

修复单只收未通过项。共同原因可以合并动作，但要列出每个受影响实例。人员签收和环境受阻不写进修复单。
