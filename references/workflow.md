# 审查流程

## 1. 冻结

`run` 只做三件事：确认输入是目录或 ZIP、把 ZIP 安全解到运行目录、记录每个文件的哈希。它不判断对错，也不写正式报告。

输出目录默认在仓库旁的 `.agent-review/runs/<run_id>/`。它必须落在仓库、依据和交付之外。已有运行不能覆盖。

## 2. 从原文建立清单

阅读 `source-inventory.json`。文本依据已经按空行分成段落，连续换行仍是同一段。PDF 要由审查者打开后，把段落和页码写进清单；脚本不声称抽取出的文字与版面一致。附件只登记哈希和用途。

每个段落恰好属于一个语义单元。一个单元可以包含连续的多段。一段里有多项可以独立判断的义务时，写成多条条款，不要拆段。

两遍核对：

1. 分类、拆分义务、决定适用性。
2. 从原文反查，检查有没有把“或 / 等 / 建议”收成“且 / 全部 / 必须”，也检查有没有把必要义务降成建议。

两遍的 `reviewer` 都填这次主审 Agent。不能写成另一位独立审查者。

## 3. 阅读交付并判断

`status` 会把适用的必要义务写成 `_internal/obligations.json`。只对这些实例下结论。建议和其他题目不会出现在这张表里。

每项记录实际读了什么、证据在哪个文件、进度和结论。通过需要交付、原题或本次执行的证据。只引用依据原文不能判通过。

## 4. 受控执行

计划必须声明 `authorization` 为 `reviewed-host-copy`，并写明已经看过的入口、读写范围和预期行为。执行器把交付复制到运行目录里再启动命令，不经过 shell。重复执行会换一份新副本。

回执里的 `sandbox` 固定为 false。退出码只说明命令本身，不说明验收通过。

## 5. 旧报告和模型更换

先把当前 `results.json` 复制为 `_internal/comparisons/baseline.json`，再读旧报告。对照记录写到 `comparisons/prior.json`，披露 `seen-prior-report`。结论有变化时，逐条写维持或修正的理由。

宿主没有提供模型标识时，运行记录写“未暴露”。主模型中途更换时，写 `model-change.json` 的原因和复核过的实例。

## 6. 收尾

`finalize` 重新从原文和清单生成预期项目，再核对结果、证据哈希和评分器处置。缺项、受阻、清单在冻结后被悄悄删改，都不会生成报告。

全部完成后得到 `review.html` 和 `repair.md`。这两份文件来自同一次结果。
